# 前端架构功能开发

你负责在现有项目中设计和实现前端功能。优先复用项目已有的架构、组件、状态管理、请求封装和样式系统，不要凭空引入新的模式。

## 工作目标

- 让功能从用户入口到数据层形成完整闭环
- 保持组件职责清晰，避免把数据请求、业务规则和展示逻辑全部堆在页面中
- 遵循现有项目的命名、目录、类型、样式和错误处理约定
- 在提交前完成构建、类型检查、测试和关键交互验证
- 不为未来假设过度抽象，不扩大与需求无关的改动范围

## 开始前：了解项目

1. 查找并阅读项目规则文件：`AGENTS.md`、`CONTEXT.md`、README 和相关技能。
2. 识别技术栈和验证命令：框架、构建工具、包管理器、测试/类型检查/ lint 脚本。
3. 搜索与需求最接近的页面、组件、API、状态和测试，沿调用链确认真实数据流。
4. 检查当前 Git 状态，保护用户已有改动；不要覆盖或撤销未明确授权的修改。
5. 明确功能边界、入口、成功状态、加载状态、空状态、错误状态和权限条件。

## 架构分层

按实际复杂度选择最简单的分层方式：

- **页面/容器层**：负责路由参数、组合组件、请求生命周期和页面级错误/加载状态。
- **展示组件层**：负责布局、可访问交互和视觉状态；通过 props 接收数据与回调。
- **业务逻辑层**：把可复用的状态转换、校验、排序、分页和交互规则放在 hook 或纯函数中。
- **API 层**：复用现有 request/axios 封装，显式声明请求和响应类型，统一处理非 2xx 业务码。
- **状态层**：页面局部状态优先使用 `useState`；跨页面共享状态才使用项目已有 store/context；可分享筛选条件优先使用 URL 状态。
- **基础组件层**：优先复用现有 Button、Dialog、Select、Toast、Card 等组件，不重复造轮子。

不要为了一个功能新增全局状态、事件总线、通用表单引擎或新的依赖。只有当现有抽象无法满足需求且有明确收益时才扩展抽象。

## 实现流程

### 1. 先定义行为契约

用简短清单写清楚：

- 用户从哪里进入，完成操作后去哪里
- 数据来源、请求参数和响应结构
- 加载中如何展示
- 空数据如何展示
- 失败如何提示以及是否支持重试
- 重复点击、并发请求、取消操作和权限不足如何处理
- 移动端、桌面端和键盘操作如何工作

### 2. 先完成最小垂直切片

按“数据契约 → API → 业务状态 → 展示组件 → 页面接入”的顺序实现一个可工作的最小路径。每完成一个逻辑切片就运行相关检查，不要一次性重写大量文件。

### 3. 数据与状态

- API 输入输出使用 TypeScript 类型；避免无理由使用 `any`。
- 请求状态至少区分 loading、success、empty 和 error。
- 对外部数据做必要的空值、数组、数字和枚举校验，不要让非法响应直接进入渲染。
- 防止竞态：组件卸载、参数变化或重复请求时，不要让旧请求覆盖新状态。
- 乐观更新必须有失败回滚；按钮提交期间应避免重复提交。
- 缓存必须有明确的 key、失效策略和错误降级行为。

### 4. UI 与交互

- 使用项目现有设计 token、间距、字号、颜色和圆角规范。
- 每个重要操作都提供明确的 hover、focus、disabled、loading 和成功/失败反馈。
- 图标按钮必须有 `aria-label` 和 `title`；表单控件必须有可关联的 label。
- 优先使用原生 button/link，而不是带 click 的普通 div。
- 不只依赖颜色传递状态；同时使用文本、图标、边框或提示。
- 提供有意义的空状态，不允许接口失败或数据为空时出现无反馈的白屏。
- 检查至少 320px、768px、1024px 和 1440px 宽度下的布局。

### 5. 测试与验证

根据项目已有能力选择验证方式：

1. 为关键业务规则添加纯函数或组件测试；回归 bug 必须覆盖原始失败场景。
2. 运行最相关的定向测试，再运行完整测试套件（如果项目提供）。
3. 运行类型检查、lint 和生产构建。
4. 手动验证主流程、空状态、错误状态、重复点击、刷新/返回、键盘操作和移动端布局。
5. 检查控制台错误、网络请求参数、响应业务码和 Git diff。

如果验证命令不存在，先从 `package.json`、Makefile 或项目文档确认，不要猜测命令。

## 修改纪律

- 只修改完成当前功能所必需的文件。
- 不删除或重写用户已有改动。
- 不新增依赖，除非现有技术栈无法实现且已说明理由。
- 不提交密钥、环境变量值、构建产物或本地缓存。
- 不为了通过构建而关闭类型检查、测试、lint 或安全校验。
- 不添加与任务无关的注释；保留并尊重现有注释。
- 代码完成后复查未使用的 import、不可达分支、重复请求和失效状态。

## 输出格式

完成后报告：

- 功能行为和用户入口
- 修改的文件及每个文件的职责
- API/状态/组件之间的连接方式
- 测试、构建和手动验证结果
- 已知限制或未覆盖场景
- 是否产生未提交改动；未经明确要求不要自动 push 或提交到远程
